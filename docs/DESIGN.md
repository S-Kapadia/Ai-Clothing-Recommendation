# Ai-Clothing-Recommendation: Design Document

Oct 27, 2026 · @Samay Kapdia

Ai-Clothing-Recommendation is a fit-aware, style-aware clothing recommender across 5 Shopify brands, built as one project covering Applied ML and SWE. It ships by Nov 11, 2026.

**Status:** design v1, replaces the earlier SPEC and HLD. Once agreed, it becomes `docs/DESIGN.md`, and Claude Code plan mode turns it into `docs/PLAN.md`. Values marked *(starting value)* are tunable in config.

## 1. Product overview

The product tells a shopper which size to buy at any of 5 brands and recommends clothes that fit their body and match their style.

**Problem.** Size labels mean different things at every brand, so shoppers guess and return. Origin: I'm tall and slim, so a size that fits my chest is usually short.

**Users.**

- **Signed-in shopper:** saves body, owned clothes and style preferences; gets personalized results everywhere.
- **Visitor (recruiter):** clicks "Try a demo persona" and sees personalized results with no login.

**Features (v1).**

| Feature | What the user gets |
| --- | --- |
| Profile | Height, weight, department; owned items with fit words; style preference chips; style weight slider |
| Search | Results across brands, filtered to items that fit, with size to buy, fit word per measurement, fit probability and a reason |
| Top X for you | A feed with no query: everything that fits, ranked by style |
| Size translation | "You wear M at Brand A, so get L at Brand B" |
| Brand fit report | "Brand C runs short in body length for you" |
| Brand filter | Search or feed limited to chosen brands |
| Demo personas | 3 synthetic shoppers viewable without login |
| Delete my data | Removes the account and everything tied to it |

**Core user flows.**

1. **First visit:** sign in with a magic link, or click "Try a demo persona".
2. **Profile setup:** enter height, weight and department; optionally add owned items (brand, item, size, fit word per measurement, wear or don't wear) and pick style chips.
3. **Search:** type "black chinos", optionally filter by category or brand, get ranked results with sizes and reasons.
4. **Feed:** open "For you" and see the top 20 items that fit, ranked by style; move the style slider to see the order change.
5. **Translate:** pick an owned item and a target brand, get the matching size and why.
6. **Brand report:** open a brand page and see how it runs for you.

## 2. Architecture

Three layers: a React web app in front, one FastAPI service in the middle, and Supabase plus an offline ML pipeline at the back. The server never runs an LLM; it only reads what the pipeline produced.

&#91;embedded content: three-layer architecture · 11 components\]

The web app reaches only the API and Supabase Auth; the pipeline writes to Supabase and the artifact store, which the API loads at startup.

**One search, end to end.**

1. The web app sends the query, filters and the user's token (or a persona id) to `POST /v1/search`.
2. The API verifies the token and loads the profile, owned items and style preferences under RLS.
3. Profile + style: body estimate (ANSUR prior, sharpened by owned items) and style profile.
4. L1: encode the query, take the FAISS top 200, drop items outside category, department, brands or fit eligibility.
5. L2: LightGBM relevance, combined with fit probability and the user's style weight.
6. Explainer: best size and reason per item; the response returns with per-step timings, and only the timings are logged.

## 5. Offline ML pipeline

The pipeline runs natively on my PC (RTX 4060, 32 GB RAM) as a sequence of re-runnable steps; each reads the previous step's output and writes its own. Every step is a CLI command, e.g. `python -m pipeline.crawl --brand <slug>`.

1. **Crawl.** `GET https://<domain>/products.json?limit=250&page=N` until empty, plus size-guide pages listed in `config/brands.yaml`. 1 request per second, robots.txt respected, user agent `ai-clothing-rec/0.1 (+repo URL)`. Raw responses saved gzipped under `data/raw/<brand>/<snapshot>/`; re-runs reuse them.
2. **Load + classify.** Upsert brands, products and variants. Category and department from rules in `config/classifier_rules.yaml` (product type, tags, title, collection names); unclear products go to Ollama with a JSON schema allowing only vocabulary values. "other" is dropped.
3. **Locate charts.** Search description HTML for tables containing size words; fall back to the brand's size-guide page. Fingerprint the normalized chart content (SHA-256) so shared charts are processed once.
4. **Normalize charts (Pillar 1).**
   1. Clean HTML table → rules parser (lxml): header detection, unit detection (cm or in), size-column mapping.
   2. Otherwise → Ollama **extract**: output schema built from the product's size list, so every size must get a row with `chest`, `body_length`, `sleeve`, `waist`, `hip`, `inseam` as nullable numbers, plus `unit` and `basis`.
   3. Ollama **review**: given the chart text and extraction, returns `ok` or a list of flags.
   4. Validators: sizes increase in order; values inside plausible ranges per dimension (config); inches × 2.54; half measurements ("pit to pit", flat waist) × 2; review flags block acceptance.
   5. Pass → `status = parsed` with confidence; fail → `abstained` with a reason, excluded from search.
5. **Map variants.** Normalize labels ("Medium" → M, "32/30" and "32 x 30" → 32x30) and set `chart_size_label`; unmapped variants are counted per brand and excluded.
6. **Extract attributes.** Ollama reads title, product type, tags and description and fills `product_attributes`; same step runs on sampled H&M articles. Rules fill what they can first (e.g. "slim fit" in the title).
7. **Generate personas.** Sample 3 male bodies from ANSUR (short and broad, average, tall and slim), assign each 5 to 8 owned items from the catalog with fit words computed by the fit model, flag `is_synthetic`.
8. **Train and build.** Body estimator, style model, ranker and embeddings (section 6), then bundle artifacts.

**Ollama setup.** Model `qwen2.5:7b-instruct` at 4-bit (Q4\_K\_M) *(starting value; confirm it fits 8 GB VRAM)*, temperature 0, `format` set to the JSON schema. Prompts live in `prompts/<name>_v<N>.md`; the version is part of the cache key.

**LLM cache.** Key = SHA-256 of (model, prompt version, input). Results stored in `data/cache/llm/<key>.json` and in `extraction_runs`. A cached key is never re-sent; changing a prompt bumps its version, which invalidates only that prompt's entries.

**Quantization benchmark.** Run step 4 on the 50 gold charts with two configurations: 7B at 4-bit and 3B at 4-bit. Report field precision and recall, abstain rate, seconds per chart and peak VRAM in `results/metrics.csv`.

## 6. ML models

Six models and scorers turn a profile and a query into ranked, sized recommendations; fit decides what is eligible, style and relevance decide the order.

### 6.1 Body estimator

Predicts six body dimensions from height and weight, with an uncertainty for each.

- **Data:** ANSUR II male. Fields mapped in `config/ansur_fields.yaml` *(verify names and units; ANSUR stores most lengths in mm)*: chest, waist and hip circumference, sleeve length, torso length, inseam.
- **Model:** one ridge regression per dimension on height, weight, height² and BMI. Saved with its residual standard deviation σ per dimension.
- **Evaluation:** MAE in cm per dimension on a 20% holdout, against a height-only regression.

### 6.2 Fit model (rule-based v1, probabilistic)

For each dimension, the fit model compares garment to body and turns the gap into one of five words and a probability.

The gap after allowing for normal looseness (ease) is the residual:

```latex
r = g - b - e_{c,f,d}
```

Here g is the garment measurement, b the body measurement, and e the ease for category c, fit type f and dimension d from `config/ease.yaml`. Word bands use two thresholds per dimension *(starting values in config)*:

| Residual r | Width word | Length word |
| --- | --- | --- |
| below -t2 | too tight | too short |
| -t2 to -t1 | a bit tight | a bit short |
| -t1 to t1 | just right | just right |
| t1 to t2 | a bit loose | a bit long |
| above t2 | too loose | too long |

**Probability.** The body is uncertain (b \~ Normal(μ, σ²) from 6.1), so r is too. The chance a dimension is acceptable ("a bit" or "just right") is:

```latex
P_d = \Phi\left(\frac{t_2 - m_d}{\sigma_d}\right) - \Phi\left(\frac{-t_2 - m_d}{\sigma_d}\right), \quad m_d = g - \mu_d - e
```

The item's fit probability is the product over its dimensions. An item is eligible if its best size has P ≥ τ (0.3, starting value).

**Owned items sharpen the body estimate.** An owned garment with a fit word implies where the body sits ("just right" means b ≈ g − e). Each one is a Normal observation combined with the ANSUR prior, so more owned items mean a smaller σ and more confident sizes:

```latex
\mu_{post} = \frac{\mu_0/\sigma_0^2 + \sum_i b_i/\tau^2}{1/\sigma_0^2 + n/\tau^2}
```

τ (observation noise) is a config value. A learned fit model replaces the hand thresholds only once closet data exists (stretch).

### 6.3 Style model (trained on H&M)

Scores how well an item matches a shopper's past purchases, using weights learned from real H&M behaviour.

- **Training data:** H&M menswear customers with 5 or more purchases. Purchases before a cutoff week form the history; purchases in the cutoff week are positives; negatives are sampled from items not bought.
- **Features per (history, candidate):** for each vocabulary attribute, the recency-weighted share of history items with the candidate's value; cosine similarity between the candidate's embedding and the mean history embedding; candidate popularity in the training window.
- **Model:** logistic regression (LightGBM if it clearly wins), giving a learned weight per attribute.
- **Evaluation:** Recall@12 and MAP@12 on held-out customers, against popularity and equal-weight attribute matching.
- **Transfer:** at serving time, history = the shopper's owned items rated wear (positive) or don't wear (negative weight), plus preference chips as extra weights. Popularity is dropped (no sales data for the 5 brands).

Style score s is in \[0, 1\].

### 6.4 Retrieval (L1)

- **Text per product:** title, product type, category, the attribute values, first 300 characters of description.
- **Embeddings:** `all-MiniLM-L6-v2` (384 dimensions), L2-normalized; FAISS `IndexFlatIP` (exact). The server encodes queries with the same model exported to int8 ONNX.
- **Query:** top 200 by similarity, then filters: category, department (requested + unisex), brands, fit eligibility.

### 6.5 Ranking (L2)

- **Learned relevance:** LightGBM LambdaRank trained on `query_labels` (grades 0 to 2), grouped by query, 5-fold cross-validation by query. Features: embedding similarity, BM25 score, query–title term overlap, category match, query mentions of attribute values that the item matches (e.g. "black" and colour family black).
- **Final score:**

```latex
\text{score} = a \cdot \text{rel} + b \cdot P_{fit} + w \cdot s
```

a and b are config values; w is the user's style weight slider (0 to 1). rel is the ranker output scaled to \[0, 1\] within the candidate set.

- **Evaluation:** NDCG@10 and Recall@50 against BM25 and embedding-only.

### 6.6 Feed, size translation, brand report, explainer

- **Top X for you:** candidates = every eligible product in the department (and chosen brands). Score = P\_fit + w·s. Diversity via maximal marginal relevance on embeddings (λ = 0.7). Return the top 20.
- **Size translation:** take an owned item, update the body estimate with it, then for the target brand and the same category return the size with the highest fit probability across that brand's products, with its words.
- **Brand fit report:** for each category the brand sells, average the residual per dimension at the user's best size; any average beyond t1 becomes a line like "runs short in body length (about 3 cm)".
- **Explainer:** templates from the predicted words, e.g. "Get the L: chest just right, length a bit long. The M would be too short."

## 7. API design

One FastAPI service exposes a versioned JSON API under `/v1`; the web app calls it through a TypeScript client generated from its OpenAPI spec.

**Auth.** The web app signs in with Supabase Auth (magic link) and sends `Authorization: Bearer <access token>`. The API verifies the token's signature with the project's JWT secret, reads the user id from `sub`, and queries user tables with that token so RLS applies. Persona endpoints need no token.

| Method + path | Auth | Purpose |
| --- | --- | --- |
| `POST /v1/search` | Token or `persona_id` | Ranked, sized results for a query |
| `GET /v1/me/feed` | Token | Top X for you |
| `GET /v1/personas/{id}/feed` | None | A persona's feed |
| `POST /v1/size-translation` | Token or `persona_id` | Size at a target brand from an owned item |
| `GET /v1/brands` | None | The 5 brands |
| `GET /v1/brands/{id}/fit-report` | Token or `persona_id` | How a brand runs for the user |
| `GET`, `PUT /v1/me/profile` | Token | Body, department, style weight |
| `GET`, `POST /v1/me/owned-items`; `DELETE /v1/me/owned-items/{id}` | Token | Owned clothes with fit words |
| `PUT /v1/me/style-preferences` | Token | Preference chips |
| `DELETE /v1/me` | Token | Delete account and all data |
| `GET /v1/personas` | None | List demo personas |
| `GET /health`, `GET /metrics` | None | Status and versions; Prometheus metrics |

**Search request and response.**

```json
{"query": "black chinos", "category": "pants", "brands": ["brand-a"],
 "k": 10, "persona_id": null}
```

```json
{"artifact_version": "v1", "catalog_snapshot": "2026-10-29",
 "results": [{"product_id": "...", "title": "...", "brand": "...",
   "image_url": "...", "product_url": "...", "size": "32x34",
   "fit_probability": 0.82, "style_score": 0.64, "relevance": 0.91,
   "fit": {"waist": "just right", "hip": "a bit loose", "inseam": "just right"},
   "reason": "Get the 32x34: waist just right, inseam just right. The 32x32 would be too short."}],
 "timings_ms": {"profile": 3, "l1": 35, "l2": 12, "total": 55}}
```

**Validation and limits.** Pydantic models on every input: query 1 to 200 characters, k 1 to 50, at most 5 brands, at most 50 owned items per user, height 140 to 220 cm, weight 40 to 200 kg. Rate limit 60 requests per minute per IP (slowapi).

**Errors.** JSON `{"error": {"code": "...", "message": "..."}}` with standard status codes: 400 invalid input, 401 missing or bad token, 404 unknown id, 429 rate limited, 500 unexpected. A catalog miss is not an error: it returns 200 with an empty list.

**Startup.** Load the artifact bundle named in `ARTIFACT_VERSION` into memory: FAISS index, product id map, measurements, attributes, embeddings, body model, ranker, style model, ONNX encoder. `/health` reports the loaded version and fails until loading finishes.

## 8. Frontend design

The web app is a React + TypeScript single-page app (Vite) with six routes; it holds no business logic and only calls the API and Supabase Auth.

| Route | View | Calls |
| --- | --- | --- |
| `/` | Landing: sign in, or pick a demo persona | `GET /v1/personas` |
| `/profile` | Body, department, owned items, style chips, style slider, delete my data | `/v1/me/*` |
| `/search` | Search box, category and brand filters, result cards | `POST /v1/search` |
| `/for-you` | Top 20 feed with style slider | `GET /v1/me/feed` or persona feed |
| `/translate` | Pick owned item + target brand, see the size | `POST /v1/size-translation` |
| `/brands/:id` | Brand fit report + that brand's feed | `GET /v1/brands/{id}/fit-report` |

**Result card.** Photo (loaded from the store's URL), brand, title, size to buy, fit probability as a percentage, one chip per measurement coloured by word (green just right, amber a bit, red too), the reason, and a "View at store" link.

**State.**

- **Session:** `supabase-js` holds the auth session and refreshes tokens.
- **Server data:** TanStack Query caches API responses and refetches after profile edits.
- **Active persona:** a URL parameter (`?persona=<id>`), so a recruiter can share a link.
- **API client:** generated with `openapi-typescript` from the API's spec in CI, so a backend change that breaks the frontend fails the build.

**Styling.** Tailwind CSS; works on mobile widths; light and dark mode.

**Tests.** Vitest + React Testing Library for the result card, filters and profile form.

## 9. Infrastructure

The web app and API run as containers under Docker Compose locally and deploy as the same images; Supabase runs from its CLI locally and hosted in production.

**Containers.**

| Service | Image | Port | Notes |
| --- | --- | --- | --- |
| `web` | Node build stage, then `nginx:alpine` serving static files | 3000 | API URL injected at build time |
| `api` | `python:3.11-slim` + `requirements-serving.txt` | 8000 | Artifacts mounted read-only from `./artifacts/<version>` |
| Supabase | Started by `supabase start` | 54321 to 54324 | Containers reach it at `host.docker.internal` |
| Pipeline + Ollama | Native, not containerized | 11434 (Ollama) | Needs the GPU |

**Environments and config.** All settings come from environment variables, never the image: `SUPABASE_URL`, `SUPABASE_ANON_KEY` (web), `SUPABASE_SERVICE_ROLE_KEY` and `SUPABASE_JWT_SECRET` (API only), `ARTIFACT_VERSION`, `CORS_ORIGINS`, `RATE_LIMIT`. `.env` is gitignored; `.env.example` lists every key empty.

**CI/CD (GitHub Actions).**

1. On every push and pull request: `ruff` + `mypy` + `pytest` (unit) for Python; `eslint` + `tsc` + `vitest` for the web app.
2. Integration job: `supabase start` via the Supabase setup action, apply migrations, run API integration tests against it.
3. Build both Docker images; fail if the generated API client is out of date.
4. On merge to `main`: push the API image to Hugging Face Spaces and deploy the web app to Vercel. The hosted database is migrated manually by me (`supabase db push`).

**Observability.**

- Structured JSON logs (structlog) with a request id on every line.
- `/metrics` in Prometheus format: request count, latency histogram per endpoint and per step.
- `request_log` table: endpoint, status, step timings, result count; no user data.
- Load test with Locust: 20 simulated users for 5 minutes against `/v1/search` and `/v1/me/feed`; p50 and p95 latency recorded in `results/metrics.csv`.

**Security.**

- Service role key and JWT secret only in the API's environment; the browser only ever sees the anon key.
- RLS on every table (section 4); the browser never queries tables directly.
- Token verification on every user endpoint; CORS limited to the web app's origin.
- Input limits and rate limiting (section 7).
- No secrets in code or images; GitHub secret scanning on.
- Delete my data removes all of a user's rows.

**Architecture decision records.** One short file each in `docs/adr/`: in-memory serving vs pgvector; local Ollama vs paid API; Supabase Auth vs custom auth; rule-based fit v1 vs learned; style trained on H\&M; MCP server design-only.

## 12. Risks and open questions

The biggest risk is time: 15 days for everything, with Pillar 1 and the H&M style work the most likely to run long.

| Risk | Effect | Mitigation |
| --- | --- | --- |
| Size charts unreadable or hidden behind pop-up apps | Fewer usable brands | Vet 8 to 10 brands, keep 5; abstain rather than guess |
| 7B model too slow or too large for 8 GB VRAM | Pipeline runs long | Fall back to the 3B model (the benchmark measures this) |
| H&M attribute extraction too slow | Style model late | Sample fewer customers; extract only articles they bought; use H&M's own columns first |
| Style weights don't transfer from H&M to the 5 brands | Weak feed | Keep the shared vocabulary strict; report H&M metrics honestly; preference chips still work |
| 50 labelled queries too few for LambdaRank | Unstable ranker | 5-fold CV with confidence intervals; fall back to tuned weights if it doesn't beat BM25 |
| Free hosting memory limits | API won't start | int8 encoder, no PyTorch; check the tier before Phase 7 |
| Scope creep | Misses Nov 11 | New ideas go to stretch unless something is cut |
